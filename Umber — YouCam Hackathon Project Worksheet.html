Umber — YouCam Hackathon Project Worksheet

Project: Umber — AI Sales Assistant for Small Retailers (WhatsApp + YouCam VTO/Skin AI) Hackathon: YouCam API Skin AI & eCommerce VTO Hackathon (Perfect Corp / Devpost), Sep 29 – Nov 2, 2026 Framework: Kenneth's Software Engineering Playbook, Phases 1–8

Phase 1 — Start With the Problem

  • Problem: Customers DM small retailers on Instagram/WhatsApp asking personalization questions ("does this suit me?", "what shade matches?"), and with no one staffing live chat, replies take hours — by then the customer has moved on.
  • User: Solo/small-team boutique or beauty retailers selling through WhatsApp/Instagram.
  • Current alternative: Owner checks DMs when free, or a generic keyword/FAQ bot that can't answer visual-judgment questions.
  • Gap/pain: Average Instagram business response time is 10+ hours; 35% of customers expect a reply within an hour; 5-minute replies convert 21x higher than hour-plus ones. Keyword bots can't close that gap because "what suits me" needs visual judgment.
  • Solution: A WhatsApp agent that, on a personalization question, requests a selfie, runs YouCam skin-tone analysis, matches the merchant's real catalog deterministically, confirms the pick with a VTO render, and replies with both.
  • Technical thesis: Because YouCam can extract objective skin-tone data and generate a photorealistic confirmation, software can now close both the personalization gap and the purchase-confidence gap — not just recommend, but prove.
  • V1 non-goals: No checkout/payment. WhatsApp only, not Instagram. No full staff-handoff system — just a clear escalation flag. No live inventory sync — a small curated product list is fine for the demo.

Phase 2 — Define Success Criteria

  1. Full round trip (inbound message → skin-tone call → catalog match → VTO render → reply) completes end-to-end for a valid request.
  2. Every documented image-failure error code from the kill test produces a graceful, specific fallback message — never a silent failure.
  3. All three escalation triggers (explicit human ask, complaint, "not satisfied" post-recommendation) fire correctly against a fixed test-message set.
  4. The general-question path never calls the YouCam API — cost stays at zero for non-personalization messages.
  5. The 15 deliberately-bad kill-test images each return the specific error code the docs promise.

Phase 4 — Architecture Before UI

Customer -> WhatsApp Cloud API -> Webhook -> Agent orchestrator -> [YouCam MCP tools] + [Catalog matcher] -> WhatsApp reply
  • Frontend: none — WhatsApp itself is the interface.
  • Backend/API: webhook receiver + agent orchestrator.
  • Storage: small catalog table + per-thread conversation state.
  • External APIs: WhatsApp Cloud API, YouCam Beauty MCP server.
  • AI layer: intent classification, reply phrasing, follow-up-question judgment.
  • Core logic: catalog matching, state transitions, escalation rules.
  • Boundary questions: the catalog matcher is authoritative on what gets recommended; the agent is authoritative on how it's said, never the reverse. A failed YouCam call degrades to a text-only reply rather than blocking the conversation.

Phase 5 — Define Data Contracts

  • Input: webhook payload — sender ID, message text, optional image URL.
  • Output: WhatsApp message — text plus optional image URL.
  • Error schema: {state, error_code, customer_facing_message, escalate: bool}
  • External API assumptions: skin-tone call returns tone/undertone JSON; VTO call returns a result URL or one of the documented preprocess/engine error codes.
  • Validation rule: an image that fails YouCam's own documented checks gets surfaced to the customer in plain language ("could you send a photo facing forward?"), not a raw error code.

Phase 6 — Model States

RECEIVED -> CLASSIFIED -> (GENERAL_REPLY | ESCALATED | AWAITING_PHOTO)

AWAITING_PHOTO -> ANALYZING -> MATCHING -> RENDERING -> SENT
  -> (CONVERTED | ALTERNATIVE_REQUESTED -> back to MATCHING | ESCALATED)
  • Failure states: ANALYZING_FAILED (bad photo) → one retake request. RENDERING_FAILED → fall back to text-only recommendation rather than stalling.
  • Terminal states: CONVERTED, ESCALATED, GENERAL_REPLY, ABANDONED.

Phase 7 — Build the Smallest Real Vertical Slice

  • Input: one hardcoded selfie, a 5-item hardcoded catalog.
  • Processing: skin-tone call → deterministic match → VTO render.
  • Output: one WhatsApp message, text plus image, sent to your own test number.
  • Definition of done: the full round trip works once, manually triggered — no webhook handler, no multi-turn logic yet.
  • Avoid premature work: no conversation persistence, no escalation logic, no FAQ path until this single path is proven.

Phase 8 — Separate Deterministic Logic From AI

  • Deterministic (code): catalog scoring/matching, state transitions, escalation rules, image pre-validation, message formatting.
  • AI: classifying what the customer is asking, phrasing the reply, deciding whether a follow-up question is needed.
  • Decision: AI only where the input is genuinely ambiguous (language, intent). Anything with a correct answer — which SKU, when to escalate — stays in code, never left to the model's judgment.

Phase 9 — Design Failure Paths Early

Generic failures from the checklist: API timeout, empty result, malformed response, invalid input, AI timeout/rate limit, bad AI output, missing fields, network failure, deployment failure.

Project-specific failures:

  1. Customer sends a screenshot or a non-selfie image. YouCam's preprocess check rejects it (error_pose / error_invalid_ref). Fallback: ask once for a real photo facing forward; if it fails twice, skip the photo and offer general best-sellers instead of stalling the conversation.
  2. error_editing_failed — the render comes back too similar to the source image. Fallback: send the text recommendation alone, without a preview image, rather than blocking or retrying indefinitely.
  3. WhatsApp's 24-hour reply window closes. If a customer goes quiet mid-flow and returns after 24 hours, free-form replies are no longer allowed — only pre-approved templates. Fallback: a short approved "we're still here, want to continue?" template to reopen the window.

General failure rules:

  • API timeout → send a "still checking" holding message rather than going silent.
  • AI misclassification (complaint vs. personalization question) → default to escalation when uncertain, never the reverse.
  • Rate limit hit (250 msgs/24hr on the test number) → track count and degrade gracefully rather than crash.

Phase 12 — Evaluate AI With Known Examples

  • Evaluation set: ~25 labeled test messages spanning all three categories (personalization, general, escalation), including edge cases: sarcasm, mixed intent in one message, typos, and code-switched phrasing (English mixed with Pidgin or other local phrasing).
  • Expected outputs prepared: Yes — each message gets a ground-truth label before the classifier sees it.
  • Actual outputs recorded: Not yet — TBD once the classifier exists.
  • Accuracy metric: Overall routing accuracy, plus escalation recall tracked separately and held to a higher bar (a missed complaint is worse than an over-cautious escalation).
  • Failure categories: ambiguous phrasing, code-switched messages, very short/no-context messages, multi-intent messages.

Rule: one successful demo message is not evidence the classifier works — only the evaluation set is.

Phase 15 — Engineering Decision Log

Decision: Scope V1 to WhatsApp only, not Instagram. Reason: Instagram's messaging API has more review friction; prove one complete path before expanding. Trade-off: Instagram-only merchants aren't covered in the demo. Revisit if: the WhatsApp path is solid with real time left before the deadline.

Decision: Rejected the "Catalog Render-Risk Auditor" idea in favor of the SMB sales assistant. Reason: the sponsor API already returns structured error codes for bad images, undermining that idea's novelty; the assistant clears the agent-necessity test better and matches real domain experience. Trade-off: gives up a B2B/inclusivity framing similar to past winners. Revisit if: the WhatsApp integration turns out to be infeasible — not expected.

Decision: Add a VTO confirmation render after skin-tone matching, rather than one API call alone. Reason: closes the purchase-confidence gap the return-rate research identified, not just padding API usage. Trade-off: adds latency (two async calls instead of one) and doubles unit cost per interaction. Revisit if: real-world latency testing shows unacceptable reply times.

Decision: Catalog matching is deterministic code, not an AI call. Reason: it has a correct answer — Phase 8's rule that code enforces rules, AI handles ambiguity. Trade-off: requires maintaining explicit match-scoring logic instead of just prompting a model. Revisit if: nothing currently anticipated.

Phase 16 — Document the Traps

Problem: Considered building a B2B tool to predict/audit VTO render failures before they happen. Assumption: The sponsor API would fail silently with no explanation, so a pre-flight auditor would add real value. Reality: The Clothes Changer API already returns specific, structured preprocess error codes explaining exactly why an image failed. Solution: Abandoned the idea before writing any code; redirected to the SMB sales assistant. Lesson: Always read the actual API docs before assuming a gap exists — Phase 6's "verify before designing" rule exists exactly for this.

Phase 19 — Review AI-Generated Code (checklist)

  • Correctness: Does the classifier's output map exactly to the three Phase 6 states? Does catalog matching implement real scoring, not a plausible-looking guess?
  • Architecture fit: Does the code respect the Phase 4 boundary — catalog matcher decides what, agent decides how, never reversed?
  • Security: Is the WhatsApp webhook's signature actually verified? Are customer selfies discarded after processing rather than retained? Is the YouCam token kept server-side only?
  • Reliability: Are the Phase 14 fallback rules actually implemented in code, not just described in a comment?
  • Maintainability: Is the Phase 6 state machine an explicit, named state enum — not scattered if/else logic?
  • Cost: Does the general-question path genuinely make zero YouCam calls, verified against the Phase 11 test row?
  • Performance: Does the polling loop stop at the 30s cap from Phase 14, rather than spinning indefinitely?
  • Testing: Does every Phase 11 row have a real executed test behind it, not just a plan?

Phase 20 — Adversarial Review Angles

  • Engineer: Does the async polling pattern hold up under real network jitter? Is conversation state actually persisted across separate stateless webhook calls, or does it silently reset?
  • Security: Could someone spam fake selfies to burn through the limited free-trial units? Could someone probe the error_nsfw_content_detected path repeatedly? Is the webhook reachable by anyone, or only Meta-signed requests?
  • Reliability: If both YouCam calls fail for a run of customers in a row, does the bot visibly degrade, or quietly become useless without anyone noticing?
  • Product: Would a much simpler auto-reply with a catalog link have been "good enough" for a real small retailer? Worth being honest here.
  • AI: Could the reply-phrasing step invent a product not in the catalog, misstate a price, or confidently claim a "match" when the underlying skin-tone read actually failed?
  • Judge: Can a stranger understand the engineering quality and the sponsor API's necessity within the first 60 seconds, without narration?

Phase 24 — Be Honest About Limitations

  1. Only tested against a WhatsApp test number with 5 verified recipients — not validated against real, unpredictable customers at scale.
  2. The curated ~15–20 item catalog is a demo-scale proxy, not a real merchant's full inventory.
  3. Skin-tone accuracy on real-world selfies (bad lighting, odd angles) is untested — the kill test only confirms failure detection works, not that successful reads are accurate.
  4. No payment or checkout — the agent recommends, it can't close the sale.
  5. Free-trial API units are finite; sustained real-world usage would need a paid plan not yet costed.

Rule: the demo video and Devpost story can only claim what was actually shown working — not what the architecture theoretically supports.

Phase 25 — Keep Complexity Proportional to Risk

Full database (e.g. Postgres) for conversation state?

  • Problem it'd solve: persisting state across restarts.
  • Risk reduced: losing context mid-demo if the server restarts.
  • Simpler alternative: SQLite or an in-memory store is enough at this scale.
  • Decision: skip Postgres. Use SQLite.

Message queue (Redis/Celery) for async polling?

  • Problem it'd solve: decoupling the webhook response from long-running YouCam polling.
  • Risk reduced: webhook timeout on slow API calls.
  • Simpler alternative: a plain async function with the 30s poll cap (Phase 14) already handles this.
  • Decision: skip the queue.

Multi-agent framework (LangGraph, CrewAI, etc.)?

  • Problem it'd solve: coordinating complex multi-agent behavior.
  • Risk reduced: none significant — the flow is a 3-way branch plus a linear pipeline.
  • Simpler alternative: a single well-structured orchestrator function calling the YouCam MCP tools directly.
  • Decision: skip the framework.
